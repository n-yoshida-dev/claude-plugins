# 画面の見た目を決める・点検する

方針は ops の `docs/2026-10-10-apps-デザイン改善の進め方.md`（5〜7 節。ユーザーの OK は Beads ops-ard.1）。
手順の形は photo-prompt-builder で 1 回通した試行（2026-10-10〜11。結果は photo-prompt-builder の `KNOWLEDGE.md` 2026-10-10・2026-10-11 と `logs/decisions.md` 2026-10-11、Beads ops-ard のコメント）で効いた部分だけにしてある。
共通にするのは進め方で、見た目はアプリごとに決める。各アプリの見た目の決まりは、そのアプリの `DESIGN.md`（Google の DESIGN.md の書式。https://github.com/google-labs-code/design.md ）にある。

## 段階ごとにやること

| アプリの段階 | やること |
|---|---|
| 画面がまだ無い | `DESIGN.md` は 3〜5 行の仮（誰がどんな場面で使うか・画面の仕事）。雰囲気の言葉と避けたい見た目はユーザーの言葉で書くので、A より前に Claude が埋めない。まず触れる画面を 1 つ通す |
| 最初の画面を作る | 骨組みが動いたら、見た目を作り込む前に A で方向を選ぶ（A は動いている画面に見本の CSS を当てて撮るため） |
| 機能を足している間 | 画面を変える PR ごとに B |
| 公開の前・人に見せる前 | 全画面を通しで B。必要なら A で見直す |
| ユーザーが見た目の作り替えを保留している | 何もしない（例：skill-matrix の「RPG らしい見た目」） |

`DESIGN.md` の無いアプリで画面を触るときは、作業の中で `DESIGN.md` を作る。今ある決まり（CSS の冒頭のコメント・`SPEC.md`・`logs/decisions.md`）を写すだけで、新しい決定はしない。一斉の作り直しはしない。
画面のファイル（.css・.tsx・.astro など）を変えると、apps-workflow のフック `look-notice.sh` がこのことを 1 セッションに 1 回知らせる。

## 道具

撮影・検出・検査・比較ページ・測定は `node "${CLAUDE_PLUGIN_ROOT}/scripts/look.mjs" <命令>` の 1 本でする（使い方は `--help`）。

| 命令 | すること |
|---|---|
| `shoot <URL> <フォルダ>` | 明るい画面と暗い画面、1280×800 と 375×812 で、1 画面分ずつ上から撮る（PNG・2 倍）。横のはみ出し・画面のエラー・外部への通信を数える。`--sizes wide,laptop,phone` で 1024×700 も足す（2 列の画面・sticky の列があるとき）。`--name current` で変更前の名前にする。`--css <見本.css>` でビルドの CSS を外して見本の CSS で撮る。`--setup <準備.mjs>` で撮る前に画面へ中身を入れる（お気に入りを 1 件保存する、など） |
| `detect <URL> <フォルダ>` | Impeccable の検出器を、画面の大きさごとに当てる。Chromium は Playwright のものを渡す |
| `lint <DESIGN.md>` | Google の DESIGN.md の検査。エラーは 0 にする |
| `page <内容.json> <出力.html>` | 見本・前と後を縦に並べた比較ページ（画像を縮めて埋めた 1 枚の HTML）を作る |
| `pixel` / `contrast` | 画素の色と、2 色の濃さの差を測る（点検役が使う） |

- 外部の道具の版（Playwright・Impeccable・`@google/design.md`）と画面の大きさは `${CLAUDE_PLUGIN_ROOT}/config/look-tools.json`。道具は表の版で `npx --yes` から呼ぶ（何を実行したかは標準エラーに出る）
- Playwright はアプリに入っているとは限らないので、表の `dir`（`~/.cache/apps-workflow/look`）に 1 つ入れて使う。無ければ `look.mjs` が入れ方の 2 行を出して止まるので、そのとおり実行する
- 画面は、そのアプリの `vite preview`（無ければ開発サーバー）を空いているポートで動かして撮る。**撮り終えたら止め、`ps` で残っていないことを確かめる**（apps の CLAUDE.md「作業の進め方」）
- 撮った画像は `~/.cache/<アプリ名>/look/<日付>/` に置く（scratchpad はセッションを開き直すと消える。photo-prompt-builder の KNOWLEDGE.md 2026-10-06）。
  比較ページの HTML だけは scratchpad に書いて Artifact に載せる（Artifact に上げられるのは作業フォルダと scratchpad の中のファイルだけ）
- 写真・個人の実データが画面に出るアプリでは、架空のサンプルの状態で撮る。画像はリポジトリに入れない

## A 方向を決める（最初の画面の骨組みが動いたら・大きな見直し）

1. **`DESIGN.md` の下書きを作る。** ひな形は app-template の `DESIGN.md`（手元の `~/workspace/apps/app-template/DESIGN.md`。無ければ `gh api repos/n-yoshida-dev/app-template/contents/DESIGN.md --jq .content | base64 -d`）。
   書き方の見本は photo-prompt-builder の `DESIGN.md`。今ある CSS・`SPEC.md`・`logs/decisions.md` から埋め、決まっていないところは「未定（A で選ぶ）」と空ける。
   ユーザーの言葉は引用で、Claude が足した言葉は「Claude の言葉」と分けて書く。`lint` でエラー 0 にする
2. **何が気になっているかを先に聞くか、見本を見せて選んでもらう。** 言葉で方向を聞かれても答えにくい（photo-prompt-builder の SPEC.md「スタイルの見本画像」の項、本人「文字だけじゃわからん。「こんな感じになるよ」って参考画像を貼ってほしい。」）
3. **大事な画面（トップ・公開して最初に見られる画面）なら、Claude だけで見本を作る前に `/apps-workflow:compete`（画面案）を 1 行で提案する**
   （例「「コンペ」か「不要」とだけ返してください」）。ユーザーが別の案・もっと良い形を求めたときも同じ。OK なら compete に進み、「不要」ならこのまま続ける
   （2026-10-12 に skill-matrix のトップ画面の作り替えで、ユーザーの「もっとかっこいいの無い？」に Claude だけで 3 案を作り、提案していなかった。
   この節の末尾に脇の 1 行で書いていたときは、提案が 1 回も無かった。経緯は ops の `docs/apps-CLAUDE-経緯.md`）。
   **見本を作る前に frontend-design のスキルを呼ぶ。** そのうえで、方向の違う見本を 2〜3 案作る。各案は、今の画面と同じクラス名で全部を書いた CSS 1 枚（`a.css` など）にし、画面の HTML は変えない
   （見本で中身が変わると、何を選んだのか分からなくなるため。選ばれた案はそのまま CSS に置ける）。飾り（テープ・印など）は `::before` / `::after` で足す。
   アプリの書体の決まり（Web フォントを読み込まない、など）は見本でも守る
4. **撮る。** 今の画面を `shoot <URL> <フォルダ> --name current`、各案を `shoot <URL> <フォルダ> --css a.css --name a` で撮る（明暗は見本の段階では明るい画面だけでよい：`--schemes light`）
5. **比較ページで見せる。** `page` で今の画面と各案を縦に並べ、非公開の Artifact に載せて URL を渡す。各案に、何を変えたかを 3〜5 行添える。
   ページの冒頭に、返してほしい言葉を書く（例：「「A」「B」「C」のどれか、部分ごとなら「条件は A、台紙は B」のように返してください」）。
   Claude Design のキャンバスは既定では使わない。試行で両方を見せたときの本人の返事は「見辛いね。」だけで、「キャンバスを使わない」「比較ページで見せる」は、そこから Claude が導いた解釈
   （photo-prompt-builder の `logs/decisions.md` 2026-10-11。並べるだけなら比較ページのほうが手間も少ない）。案を部品ごとに動かして見比べたい、とユーザーが言ったら見直す
6. **選ばれたら確定する。** `/decide` で台帳に残す（ユーザーの言葉をそのまま。取り込むときに Claude が足した・変えたことは「ユーザーは未確認」と分ける）。
   選んだ CSS をアプリに入れ、暗い画面の色など見本に無かった部分を足し、`DESIGN.md` を確定する（`lint` でエラー 0）。そのまま B を通し、前と後の比較ページを見せる

## B 毎回の点検（画面のファイルを変えた PR の前）

見た目が変わらない変更（.tsx の中の処理だけ、など）なら B は省き、PR 本文にそう書く。

1. `DESIGN.md` を読む。新しい画面か大きな作り替えなら、作る前に frontend-design のスキルも呼ぶ
2. **変更前を撮る。** 画面のファイルを触る前に `shoot <URL> <フォルダ> --name current` で撮っておく。
   撮り忘れたときは、main を別の作業フォルダに出し（`git worktree add <一時フォルダ> main`）、そこでビルドして動かした画面を `--name current` で撮る（撮ったら止めて `git worktree remove`）。
   アプリの CSS がそのファイル 1 枚だけ（部品ごとの CSS・ライブラリの CSS が無い）で HTML を変えていないなら、`git show main:<CSS のパス> > <フォルダ>/before.css` を今の画面に `--css <フォルダ>/before.css --name current` で当ててもよい
   （`--css` は画面の CSS を全部外すので、CSS が複数あるアプリでは変更前の見た目にならない）
3. **変更後を撮る。** `shoot <URL> <フォルダ>`（2 列の画面・sticky の列があるなら `--sizes wide,laptop,phone`）。
   そのアプリだけの確かめ（右の列が画面に収まるか、行のどこを押しても選べるか、など）は `--setup` の関数に書き、結果を文字列で返す。
   出力の「横のはみ出し」「画面のエラー」「外部への通信」を読む
4. **点検役と検出器を並べて回す。** 検出器（`detect <URL> <フォルダ>`）は Bash のバックグラウンド実行で流し、その間に Agent ツールで点検役を呼ぶ。
   拾うものが違うので両方当てる（試行では、クリーム色の地は検出器だけが拾い、`box-shadow: inset` で描いた左の色帯は検出器が拾わず、点検役は画素を測って十数件を返した）。
   点検役に渡す差分は `git diff main -- <変えた CSS・TSX> > <フォルダ>/change.diff` で作る

   ```
   subagent_type: apps-workflow:look-reviewer
   prompt: アプリ：<名前>（<誰がどんな場面で使う、何をする画面か>）。今回の変更：<何を変えたか>。
   DESIGN.md：<絶対パス>
   変更後の CSS：<絶対パス>、変更前との差分：<フォルダ>/change.diff
   画面の構造：<App.tsx と部品のファイル>
   画像：<フォルダ>。変更後は wide-1〜n（1280×800 明るい画面、上から順に）・phone-1〜n（375×812）・wide-dark-1〜n・phone-dark-1〜n（暗い画面）。変更前は current- を頭に付けたもの
   look.mjs：${CLAUDE_PLUGIN_ROOT}/scripts/look.mjs
   ```

5. **直す。** 点検役の「直すべき」と検出器の指摘のうち、決まり（`DESIGN.md`）か基本（濃さの差・押せる大きさ・はみ出し・フォーカス）に反するものは直し、3〜4 を回し直す。
   **直すのは 2 回まで。** 3 回目でも残るものは、直さずに PR 本文と報告に書く。
   直し方が見た目の判断になるもの（点検役が案を並べたもの）は、Claude が 1 つ選んで直し、選んだことを `DESIGN.md` と KNOWLEDGE.md に「Claude が選んだ」と書いて、6 の比較ページにも載せる
   （台帳には書かない。ユーザーの決定ではないため。試行では、暗い画面で台紙が紙に溶ける指摘に、台紙の縁へ細い線を引く案を Claude が選んだ）
6. **好みの問題は直さない。** 前と後の比較ページ（`page`。前と後を 1 組ずつ横に並べる）を作って非公開の Artifact に載せ、URL を PR 本文と報告に書いてユーザーに見せる。好みの問題が無ければページは作らなくてよい
7. **PR 本文の「確認した証拠」に 1 行で書く。** 例：「見た目の点検：はみ出し 0・画面のエラー 0・外部への通信 0／点検役 直すべき 4 件（直した）・好みの問題 3 件（比較ページ <URL>）／Impeccable 0 件（直す前は 2 件）」
8. 点検で見つけた「AI がよく作る形」は、`DESIGN.md` の「避ける形」に足していく

## 比較ページの内容（`page` に渡す JSON）

```json
{
  "title": "写真帳の見た目",
  "lead": "見本 3 案を今の画面と並べました。",
  "ask": "「A」「B」「C」のどれか、部分ごとなら「条件は A、台紙は B」のように返してください",
  "notes": ["画像は Linux で撮ったので、日本語は Noto の書体で描かれています（お使いの端末では OS の書体になります）"],
  "sections": [
    {
      "tag": "A",
      "heading": "写真帳の 1 ページ",
      "lead": "今の題材を研ぎ澄ます案。",
      "points": ["箱をなくし、罫線と余白で区切る", "選んだ行の印は写真のコーナー"],
      "rows": [
        [{ "src": "a-wide-1.png", "caption": "PC" }],
        [{ "src": "a-phone-1.png", "caption": "スマホ" }, { "src": "a-phone-2.png", "caption": "スマホ（続き）" }]
      ]
    }
  ]
}
```

- `rows` の 1 行が横に並ぶ 1 組（前と後なら `[{前}, {後}]`）。狭い画面では縦に並ぶ。画像のパスは JSON の場所から見た相対パスでよい
- `title` は Artifact の名前になる。2〜4 語の名前にし、説明は publish の `description` に書く
- Artifact の上限に近づくと止まる（値は表の `artifact`。2026-10-11 時点で上限 16MB、止めるのは 15MB）。画像を減らすか 2 ページに分ける

## ハマりどころ（試行で踏んだもの）

- 行を押して確かめたあとにそのまま撮ると、マウスのある行に hover の色が付き、選んでいない行が選ばれて見える。`shoot` は撮る前にマウスを左上の隅へ動かす。`--setup` の中で撮るときも同じにする
- 行全体を押せるようにラベルの `::after` で覆うと、覆いがラジオの上にも来て、Playwright の `check()` が「別の要素が上にある」と止まる。ラジオに `position: relative; z-index: 1` を付ける。一文の上を押す確かめは、要素ではなく画面上の位置を `page.mouse.click` で押す
- この WSL には日本語の書体が Noto Sans / Noto Serif CJK しか無い。明朝の見本は描けるが、丸ゴシックなどは描けない。見本に「お使いの端末では OS の書体で出る」と書く
- 検出器は CSS のファイルに当てると 0 件になる（描いた画面を見る作り）。動いている画面の URL に当てる
- `lint` が見るのは書式・参照切れ・部品の文字と背景の濃さの差だけで、見た目の良し悪しは見ない。部品（`components`）に文字と背景の組を書くと、その濃さの差も見る
- `DESIGN.md` の YAML は明るい画面の値だけ（書式に暗い画面の欄が無い）。暗い画面の値は本文の表と CSS に書く

## しないこと

- Impeccable のプラグイン（スキル）は入れない。検出器だけを `detect` で呼ぶ（説明がどの作業でも読み込まれる・小さな依頼にも長い手順・質問の画面で聞く。進め方の文書 4 節）
- UI UX Pro Max・shadcn/ui Blocks・21st.dev は入れない。有料の Mobbin・Refero は使わない（同 4 節。手本が足りないと感じたら、Refero を 1 か月だけ試すのをユーザーに提案する）
- 動きの足しすぎ（Motion・React Bits を既定で入れる）をしない。必要な画面が出たら、そのアプリで決める
- 好みの問題を Claude が直して完了にしない。ユーザーに見せる
